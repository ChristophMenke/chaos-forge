# Rückgängig/Wiederherstellen — Implementation Plan

## Overview

Zwei Pfeil-Buttons in der Modus-Leiste (Verwalten/Spielen/Episch) machen Änderungen am eigenen Charakter rückgängig bzw. stellen sie wieder her, wie in Office. Die Historie gilt pro Charakter und Browser-Tab, bleibt beim Moduswechsel erhalten und verfällt beim Neuladen. Keine Tastenkürzel.

## Current State Analysis

Siehe `docs/agents/research/2026-10-05-undo-redo.md`. Kernpunkte:

- Keine Undo-Infrastruktur, keine Toasts mit Aktion, kein seitenübergreifender State.
- Komponenten schreiben direkt per Supabase; der Vorher-Wert liegt fast immer im lokalen State.
- Alle betroffenen Tabellen haben `id uuid` als Primärschlüssel, außer `character_spells` (`(character_id, spell_id)`, 00004).
- `/characters/[id]/{manage,play,epic}` haben kein gemeinsames Layout; `src/app/characters/layout.tsx` umschließt alle Charaktere.
- `PlayMode`, `CharacterSheet`, `EpicEquipmentView` halten Daten in `useState(initial…)` — ein `router.refresh()` setzt sie nicht zurück.
- `CharacterSheet` arbeitet mit Entwurf + „Speichern“ (`update()` → `dirty` → `handleSave` mit `buildCharacterSaveFields`). **Voraussetzung:** PR #180 ist gemerged und `feat/undo-redo` auf `main` rebased.
- Tabs (Base UI `Tabs.Panel`, `ui/tabs.tsx:65`) werden beim Verstecken ausgehängt; `tab-proficiencies.tsx:144-146`, `tab-spells.tsx:206/226` und `blade-system-card.tsx:49-50` kopieren Props in eigenen State.
- Play Mode hält `characterClasses`, Fertigkeiten, Kampfstile und `epicItems` als Props (`play-mode.tsx:215-249`), nur `character`, `spells`, `equipment`, `inventory` als State.
- `LevelUpPlan` enthält nur Nachher-Werte; `xp-add-dialog.tsx:162` fügt `xp_history` ohne `.select()` ein; `endEffect`/`endAllEffects` liefern keine Zeilen zurück.
- NPC-Seiten unter `/master/npcs/[id]/{manage,play}` nutzen dieselben Komponenten.
- `effects-api.ts` liefert bereits `before`/`after`; `character_effects` nutzt Soft-Delete (`ended_at`), Realtime ignoriert DELETE.

## Desired End State

- In der Modus-Leiste eigener Charaktere stehen „↶“ und „↷“. Deaktiviert, wenn nichts da ist; Tooltip/`aria-label` „Rückgängig: TP −5“ bzw. „Wiederherstellen: …“.
- Klick schreibt den vorherigen Zustand in die DB (Konfliktprüfung), aktualisiert die offene Ansicht sofort und zeigt kurz „Rückgängig: X“ / „Wiederhergestellt: X“ (sonner, wird vorgelesen).
- Hat jemand den Wert inzwischen geändert: nichts schreiben, Hinweis „Kann nicht rückgängig gemacht werden – wurde inzwischen geändert“, Schritt fällt aus der Historie.
- Max. 50 Schritte; eine neue Änderung verwirft die Wiederherstellen-Schritte; schnelle Änderungen am selben Feld (< 1 s) bilden einen Schritt.
- Charakterbogen: ungespeicherte Eingaben Schritt für Schritt rückgängig; beim Speichern werden sie zu einem Schritt „Charakterbogen gespeichert“; beim Verlassen ohne Speichern verfallen sie.

## What We're NOT Doing

- Keine Tastenkürzel (Entscheidung User).
- Keine Undo-Toasts statt Bestätigungsdialogen; alle Rückfragen bleiben.
- Nicht umkehrbar: Charakter löschen/duplizieren, Avatar, Rescan, Teilen/Öffentlich, Archivieren (`is_active`), Gold/Item an andere senden, `last_accessed_at`.
- Katalogeinträge (eigene Waffe/Rüstung/Zauber/NWP in `weapons`, `armor`, `spells`, `nonweapon_proficiencies`) bleiben beim Rückgängigmachen bestehen; nur der Eintrag am Charakter wird entfernt.
- Party, Chronik, GM-Dashboard, Einstellungen, NPC-Seiten im GM-Bereich.
- Keine Persistenz der Historie (kein sessionStorage, keine Tabelle), keine Migration.
- Keine Transaktionen: Ein Schritt mit mehreren Zeilen wird nacheinander geschrieben (wie die Original-Aktion).

## Architecture and Code Reuse

```
 Komponente ──write ok──► undo.record({label, changes[], coalesceKey})
                                   │
              UndoProvider (characters/[id]/layout.tsx, key = characterId)
                 history (pure)  ◄─┘
   [↶] ─► undo() ─► applyChanges(supabase, entry, "undo")   (lib/undo/apply.ts)
                        │ 1. alle Zeilen laden + mit erwartetem Zustand vergleichen
                        │ 2. schreiben (update / delete / insert / soft-delete)
                        ▼
                 emit(changes, direction) ──► useUndoSync(handler) in PlayMode,
                                              CharacterSheet, EpicEquipmentView,
                                              Tabs → patchen lokalen State
```

- **`RowChange`** (ein Datensatz): `{ table, key: Record<string,string>, before: Row|null, after: Row|null, uiBefore?, uiAfter? }`
  - `before=null` → Insert, `after=null` → Delete, sonst Update (nur geänderte Spalten in `before`/`after`).
  - `uiBefore/uiAfter`: das UI-Objekt inkl. Joins (z. B. Equipment mit Waffe), damit die Ansicht ohne Nachladen gepatcht werden kann.
- **`UndoEntry`**: `{ id, label: {key, values}, changes: RowChange[], coalesceKey?, at, kind: "db" | "draft" }`.
  - `draft`-Einträge (Charakterbogen-Entwurf) schreiben nicht in die DB, sondern gehen nur an den Sync-Handler.
- **Tabellen-Konfiguration** `TABLES` (lib/undo/tables.ts): erlaubte Tabellen + Schlüssel + `softDelete` (`character_effects` → `ended_at`) + Join-Felder, die vor einem Re-Insert entfernt werden (`weapon`, `armor`, `spell`, `item`, …).
- **Regeln für Schreibstellen**:
  - Nur nach erfolgreichem Write aufzeichnen, immer mit den Zeilen, die die DB zurückgibt (`.select()`), nicht mit lokal erzeugten Werten (Zeitstempel!).
  - Eine Nutzeraktion = ein Eintrag: Schreib-Helfer geben ihre `RowChange[]` zurück, der Aufrufer zeichnet einmal auf (z. B. Schaden = temporäre TP + TP; Ausrüsten epischer Items = Item + TP-Clamp; Bezahlen = fünf Münzfelder).
  - Vorher-Werte kommen aus dem State vor dem Write (Snapshot), nie aus Plan-Objekten, die nur Nachher-Werte kennen.
  - Felder, die bei jedem Tastendruck schreiben (Menge, Treffer-/Schadensbonus), schreiben künftig entprellt (400 ms) und zeichnen danach auf.
- **Konfliktprüfung**: Vergleich nur der Spalten des Eintrags; Soft-Delete-Spalte nur „gesetzt / nicht gesetzt“. Unique- oder FK-Verletzung beim Re-Insert (`23505`/`23503`) zählt als Konflikt.
- **Nach jedem Undo/Redo**: Listener patchen den lokalen State (idempotent), danach `router.refresh()` für Daten, die nur als Props vorliegen.
- **Coalescing**: gleicher `coalesceKey`, letzter Eintrag ist der oberste, kein Undo/Redo dazwischen und `now - last.at < 1000` → zusammenführen (erstes `before`, neues `after`, `at` = jetzt, d. h. zusammenhängendes Tippen bleibt ein Schritt). Ergibt die Zusammenführung keine Änderung mehr (10→9→10), entfällt der Eintrag.
- **Während `busy`** (Undo/Redo läuft) sind die Buttons deaktiviert; `record` wird gepuffert und nach Abschluss angehängt.
- Wiederverwendung: `effects-api.ts` (`before`/`after`), `buildCharacterSaveFields`, `LevelUpPlan`, `sonner`, `Tooltip`/`Button` (shadcn), `useTranslations`.
- Keine neue Library (zundo/redux-undo verwalten nur Client-State, siehe Research).

## Performance Considerations

- Historie im Speicher, max. 50 Einträge; Coalescing verhindert Einträge pro Tastendruck.
- Pro Rückgängig ein SELECT je Zeile für die Konfliktprüfung (meist 1–3 Zeilen).
- Layout lädt nur `characters.user_id` (eine kleine Abfrage, per React `cache()` mit der Seite teilbar).

## Migration Notes

Keine Migration. RLS erlaubt dem Besitzer bereits INSERT/UPDATE/DELETE auf allen betroffenen Tabellen; Wiederherstellen einer gelöschten Zeile nutzt dieselbe `id`.
